## CRITICAL: Release and test policy — test releases first, MCP-only formal validation

1. **No tests before or as a gate for test/beta/prerelease publication.** A test release exists to get a new installable build onto every supported platform quickly. Do not run unit, integration, simulator, emulator, Playwright, packaged-app E2E, smoke, regression, or other test suites merely to authorize a test release. Build/sign/package/provenance/ancestry/integrity checks are allowed because they are release construction, not product-behavior tests.
2. **All automatic E2E and other long-running test workflows are disabled by default.** E2E workflows must be `workflow_dispatch`/manual-only unless a later explicit user requirement re-enables a specific automatic gate. They are not required before test releases and must not be triggered automatically by PR, merge-group, push, `main`, `workflow_run`, scheduled, or release events.
3. **Do not use workflow-authored autonomous E2E as the formal-release acceptance authority.** When a formal/stable release actually needs behavioral verification, start the appropriate GitHub Actions interactive Runner manually. The Runner must install/launch the exact candidate application and the installed Fabushi application itself must register the corresponding controllable device/tool surface.
4. **Behavioral release testing is driven from ChatGPT through the Fabushi official MCP.** The agent must call the official Fabushi MCP to discover the Action-owned/App-owned device, inspect its advertised tools, operate the installed application as a real user, record notes/evidence, and explicitly finish the remote session. The Action runner provides the device and evidence boundary; it must not silently replace the MCP-driven test with self-authored simulated-user E2E.
5. **Formal/stable publication is allowed only after the required MCP-driven device checks pass for the exact candidate source/artifact lineage.** If the Fabushi official MCP cannot connect, the required Action-owned device does not appear, the application cannot be controlled, or a required MCP-driven check fails, keep the formal release blocked. Never infer a pass from an older run, a different SHA, source-only CI, or an autonomous E2E run.
6. **Test release and formal release are distinct gates.** The required order is: merge accepted work -> publish a monotonically newer all-platform test release with no behavioral tests -> manually start the exact-candidate interactive Action runner(s) -> use Fabushi official MCP to control the installed app/device and test -> publish/promote the formal stable release only after those MCP checks pass.
7. **Manual E2E remains available only when explicitly needed.** A human/user may request a specific E2E investigation, or a task may require it for debugging, but it stays manual and advisory unless the latest explicit requirement promotes that exact workflow to a gate. Do not restore repository-wide automatic E2E implicitly.
8. **Fast-path requirement.** Disable or manualize workflows whose primary purpose is long-running test/E2E validation when they are not needed for the current release. Keep only the minimum build/sign/package/provenance/security steps needed to construct and distribute artifacts. Do not spend release time on duplicate platform builds or duplicate test suites when an exact candidate artifact can be reused.
9. **Evidence.** Formal MCP validation must retain the exact source SHA, app version, Action run/job, App-owned device ID, MCP tool/action trace, screenshots/video/logs where supported, test notes, finish signal, and pass/fail result. Test releases must retain source SHA/version/artifact/signing/provenance evidence but deliberately have no behavioral-test requirement.
10. **No local builds/tests.** The legacy local-disk prohibition remains in force. Build/package on GitHub Actions; when formal behavioral testing is needed, use the Fabushi official MCP against Action-owned/App-owned devices.

## CRITICAL: Ordinary devices are control/edit surfaces, never build surfaces

1. **Never compile, build, package, or run build-producing tests on an ordinary/persistent device.** An ordinary device is any long-lived developer workstation, personal Mac/Windows computer, VPS/server, production/service host, MCP host, or other machine not explicitly provisioned as a disposable build runner. This explicitly includes persistent hosts such as `bhrum2`.
2. **Disk-consuming toolchains belong only on GitHub Actions or an explicitly designated disposable build runner.** Do not run `cargo build/check/test`, Gradle/Android builds, Xcode builds, `npm`/`pnpm`/`yarn` build/test flows, Electron packaging, Docker image builds, browser/E2E dependency installs, native packaging, or equivalent compiler/package pipelines on ordinary devices.
3. **Do not populate large build/dependency caches on ordinary devices.** Do not create or warm large `target/`, `node_modules/`, Gradle, DerivedData, emulator/simulator, Playwright/browser, Docker-build, package-manager, compiler, or duplicated full-worktree caches merely to validate or build a change. Do not install/download large build dependencies there when the same work can run on Actions.
4. **Allowed ordinary-device work is low-footprint control-plane work only.** Source inspection, `git fetch/show/status/diff`, small text edits, GitHub/API orchestration, reading logs, service health checks/restarts, and deploying already-built bounded artifacts are allowed. Small static/text/config checks such as `git diff --check` are allowed only when they do not compile code, install dependencies, or materially grow disk usage.
5. **If compilation or artifact construction is required, dispatch it to Actions instead of making space locally.** Low disk space is a stop signal, not a reason to delete files and then continue a local build. Cleaning a persistent host may restore service health, but must not be followed by build/cache recreation on that host.
6. **Persistent-host deployments must remain bounded and rollback-safe.** Reuse already-built immutable artifacts, inspect free space before staging material artifacts, avoid duplicate copies when possible, and remove superseded temporary/staging data after successful atomic activation. Never sacrifice service/database/source data to make room for a build.
7. **No implicit exception.** A local/persistent build is allowed only when the user explicitly designates that specific machine as a disposable build runner for that task. Otherwise fail closed and move the build to GitHub Actions.

## CRITICAL: Completion semantics for release work

For application-affecting tasks, merge and canonical-main readback remain required. Under this policy, a **test release** may be completed once exact-source all-platform packages/test-distribution artifacts are published with release integrity evidence and without tests. A **formal release** may be completed only after the exact candidate has passed the required MCP-driven Action-runner device validation and the stable release is published. An MCP connectivity failure or missing controllable runner device is a blocker, not permission to fall back to automatic E2E.

All non-conflicting instructions in `AGENTS.legacy.md` remain mandatory.
