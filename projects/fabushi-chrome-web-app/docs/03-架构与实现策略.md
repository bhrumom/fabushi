# 架构与实现策略

service-worker.js 只组合三个互不污染的模块：
1. platform-bridge.js -> com.fabushi.chrome_platform -> ChromePlatformServer /
   Coordinator transport adapter。Grok parity cutover 后，Agent/Chats 不再由该桥直接把
   renderer 接到 Host，而是统一进入 Mahayana Coordinator -> Host；Native Messaging
   仅是 local transport / local capability adapter。
2. browser-control.js -> com.fabushi.browser_control -> browser-extension-host.mjs
   -> browser-extension-bridge.js -> Computer Browser MCP，负责标签、CDP、OOPIF、下载和生命周期。
3. userscript-runner.js + userscript-core.js + userscript-content.js -> Chrome userScripts/scripting
   API，保留 0.4.1 的导入、自动确认、启停、页面握手和脚本调用合同；脚本源随
   Fabushi 包发布，禁止运行时从任意 URL 加载可执行代码。

两个 native hosts 共享 per-user secret 但使用不同名称和 socket。平台服务器校验已安装
Fabushi extension ID，并只转发允许的桌面方法；扩展永远不接触长期凭据。

CWA-007 增加 `account-browser-agent.js`。它调用现有 Fabushi browser-login API，
只把短期 access session 放在 `storage.session`，再连接官方 `/browser-agent`。
网关先校验稳定发布扩展 origin 和首帧账号凭证，再允许注册；MCP 调用复用
`browser-control.js` dispatcher。退出、失效或换账号会断开 socket、撤销 claims、
detach debugger 并轮换 generation，不关闭用户标签页。见 ADR-0002。

浏览器模块保留旧命令/事件合同，并给每次列表和 claim 加 generation。标题、URL、
generation、未认领标签、非 HTTP(S) 页面或错误 origin 均 fail closed。创建的自动化
标签继续使用分组和 retain/release 语义，用户标签不被关闭。安装器只把
chrome-platform/extension 作为活动包并落到私有的 fabushi-extension 目录，旧
extension 目录保留作回滚和迁移参考；只有 UI 验收后 cleanup-legacy 才会将旧目录移入
Trash。未配置发布 Web Store ID 时，桌面平台服务器拒绝启动账户桥。

### CWA-008 userscript recovery capability

`userscript-content.js` 只把页面内 `fabushi-userscript` 的
`recovery-capability.request/release` 转发给 MV3 service worker；它不把任务正文、prompt
或文件内容传出。`userscript-recovery.js` 在 service worker 页面外维护短期 owner/tab lease，
使用 `tabs.onUpdated`、`tabs.onRemoved`、`discarded`、崩溃 URL/标题和 `alarms` 观察异常。
宿主校验请求来自 ChatGPT HTTPS 页面，恢复 URL 只能是 ChatGPT `/` 或 `/c/<id>` 加一次性
`fabushi-resume` hash；发现异常时先 `tabs.update` 原 tab，失败才 `tabs.create` 一次接管。

脚本侧的 localStorage heartbeat 是恢复索引，任务目标和附件字节仍分别留在任务存储与
IndexedDB。新文档通过恢复票据重新取得同一 workspace owner 和 Web Lock；发送确认超时
任务保留原 token，当前唯一会话的显式恢复绑定 URL 后进入 inspect，Work final 由脚本
写入 `task.result` 并进入新的 planner/acceptance conversation。


## CWA-013 — Grok Bot 0.18 Chrome extension architecture

Canonical detail: `08-grok-bot-0.18-extension-architecture-product-parity.md`.

### Primary product shell

插件主入口必须是完整 extension page 的 Grok-shaped Agent workspace。toolbar action
打开完整应用；popup 若存在，只能承担 launcher/status/quick action，不能作为主 Agent UI。

现有 Chats/Mini Apps/Marketplace/Browser/Settings 壳最终不得与 Grok UI 形成两个并行
主产品。Browser、Mini Apps、Marketplace、Userscripts 和账号状态必须整合到 Grok-style
navigation/context/settings/tools surfaces，同时保持原功能合同。

### Runtime ownership

```text
Full-page Extension Renderer
        -> typed Extension Platform Runtime
        -> MV3 Service Worker (thin broker)
        -> local Native Messaging OR remote HTTPS/WebSocket
        -> Mahayana Coordinator
        -> Host
        -> Runner / MCP / Browser Control
```

Service Worker 不拥有 durable turn、transcript、retry/provider truth。Chrome suspend/restart
worker 后必须从 Coordinator/Host resync。renderer 也不得直连 Host/Runner。

local Native Messaging 与 remote transport 必须共享同一 request/reply/event/streaming/cancel/
reconnect/resync 合同，不能形成“桌面聊天”和“远程聊天”两套状态机。桌面不在线时，
remote Coordinator/Host 仍需提供核心 Grok Agent 能力。

### Approved extension capabilities

Grok parity 不触发“删除非 Grok 功能”的默认规则。以下是明确批准保留的 extension
capabilities：

- Browser Control 九命令/八动作；
- generation/title/URL claim fencing；
- CDP/OOPIF/download/tab ownership；
- userscript import/install/update/enable/disable/recovery；
- Mini Apps / Marketplace；
- Fabushi independent browser login；
- same-account official MCP / cross-account denial；
- optional desktop/native enhancement。

这些能力通过 typed tools/context/settings/plugin surfaces 接入 Grok UI/Host，但不得破坏
原安全合同。

### Language

Renderer/UI/Chrome APIs/Service Worker 优先 TypeScript/React；userscript 保持 JavaScript
格式；Mahayana Coordinator/Host/Runner 优先 Rust；Native Messaging adapter 根据现有
平台接口选择 TypeScript/Node 或 Rust。语言不作为 parity 证据。

### Migration semantics

逐 Grok 源文件建立 ledger，但不要求一对一目标文件。允许 one-to-many / many-to-one，
前提是 Grok boundary、责任、状态机与可观察 UI/产品效果没有被折叠或丢失。
`not-applicable` 只针对平台机制；只要用户效果仍适用于 Chrome，就必须给出
replacement behavior 与生产证据。
