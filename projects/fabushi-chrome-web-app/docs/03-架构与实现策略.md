# 架构与实现策略

service-worker.js 只组合三个互不污染的模块：
1. platform-bridge.js -> com.fabushi.chrome_platform -> Electron ChromePlatformServer
   -> Mahayana Host，负责账户、Chats、Mini Apps、Marketplace 和设置。
2. browser-control.js -> com.fabushi.browser_control -> browser-extension-host.mjs
   -> browser-extension-bridge.js -> Computer Browser MCP，负责标签、CDP、OOPIF、下载和生命周期。
3. userscript-runner.js + userscript-core.js + userscript-content.js -> Chrome userScripts/scripting
   API，保留 0.4.1 的导入、自动确认、启停、页面握手和脚本调用合同；脚本源随
   Fabushi 包发布，禁止运行时从任意 URL 加载可执行代码。

两个 native hosts 共享 per-user secret 但使用不同名称和 socket。平台服务器校验已安装
Fabushi extension ID，并只转发允许的桌面方法；扩展永远不接触长期凭据。

CWA-007 增加 `account-browser-agent.js`。它调用现有 Fabushi browser-login API，
只把短期 access session 放在 `storage.session`，再连接官方 `/browser-agent`。
网关先校验稳定发布扩展 origin 和首帧账号凭证，再允许注册；MCP 调用复用
`browser-control.js` dispatcher。退出、失效或换账号会断开 socket、撤销 claims、
detach debugger 并轮换 generation，不关闭用户标签页。见 ADR-0002。

浏览器模块保留旧命令/事件合同，并给每次列表和 claim 加 generation。标题、URL、
generation、未认领标签、非 HTTP(S) 页面或错误 origin 均 fail closed。创建的自动化
标签继续使用分组和 retain/release 语义，用户标签不被关闭。安装器只把
chrome-platform/extension 作为活动包并落到私有的 fabushi-extension 目录，旧
extension 目录保留作回滚和迁移参考；只有 UI 验收后 cleanup-legacy 才会将旧目录移入
Trash。未配置发布 Web Store ID 时，桌面平台服务器拒绝启动账户桥。

### CWA-008 userscript recovery capability

`userscript-content.js` 只把页面内 `fabushi-userscript` 的
`recovery-capability.request/release` 转发给 MV3 service worker；它不把任务正文、prompt
或文件内容传出。`userscript-recovery.js` 在 service worker 页面外维护短期 owner/tab lease，
使用 `tabs.onUpdated`、`tabs.onRemoved`、`discarded`、崩溃 URL/标题和 `alarms` 观察异常。
宿主校验请求来自 ChatGPT HTTPS 页面，恢复 URL 只能是 ChatGPT `/` 或 `/c/<id>` 加一次性
`fabushi-resume` hash；发现异常时先 `tabs.update` 原 tab，失败才 `tabs.create` 一次接管。

脚本侧的 localStorage heartbeat 是恢复索引，任务目标和附件字节仍分别留在任务存储与
IndexedDB。新文档通过恢复票据重新取得同一 workspace owner 和 Web Lock；发送确认超时
任务保留原 token，当前唯一会话的显式恢复绑定 URL 后进入 inspect，Work final 由脚本
写入 `task.result` 并进入新的 planner/acceptance conversation。

### CWA-009 marketplace security admission

发布者提交版本时，Worker 只写入 `plugin_releases.release_status=pending`、
`security_scan_status=pending` 和不可变 GitHub artifact 元数据；公共列表、元数据、
下载、安装和路由都要求 `approved` + `passed`。GitHub 继续托管源码、Release 和安装包，
市场 D1 不保存二进制副本。

自有安全服务器以受限服务账号轮询 `/v1/marketplace/security/queue`，通过受保护 token
claim 精确的插件/版本/SHA/大小，从 GitHub 允许域名逐跳下载并校验。服务先安全解包，
再执行宿主 ClamAV、无网络只读无特权容器中的 Gitleaks/Syft/动态探针，以及仅用于 OSV
元数据查询的独立联网容器。扫描器没有发布 token、用户凭据或 Cosign 私钥。

所有检查通过后，服务器用本机 Cosign 私钥签名同一主包并用公钥立即验证，再把脱敏结果、
固定服务名、服务器实例、服务源码 SHA、包摘要和 bundle 回写 Worker。Worker 校验固定
服务契约、公钥文件 SHA-256、key ID、四项检查和 claim，使用 D1 batch 原子提升版本为
`approved/public`；复扫失败则进入 `revoked`，公共接口立即拒绝并选择最近仍通过的版本。
Docker 限制是防御纵深；高风险多租户动态执行后续迁移到 Firecracker/等价 micro-VM。
