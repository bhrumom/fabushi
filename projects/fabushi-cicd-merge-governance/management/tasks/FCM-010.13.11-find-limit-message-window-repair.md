## Production blocker

The production `fabushi.app.find` schema accepts `limit <= 100`. The original external journey emitted `limit=200`, so the real production MCP correctly failed closed. PR #2553 introduced a shared serialization boundary that clamps/defaults valid find requests to `1..100` and rejects invalid non-positive/non-integer limits.

Independent exact-head review then exposed a second correctness issue: a broad `find({ role: "article", limit: 100 })` returns the first 100 matching DOM elements. Messenger rows are rendered oldest-to-newest, so a persistent conversation with more than 100 rendered rows can hide the newly appended assistant response from both the baseline and incoming-message poll.

A later exact-head review exposed the final identity bug in that repair: filtering every new row with `!text.includes(ownText)` also rejects a legitimate assistant echo response (`收到：<prompt>`). The implementation now resolves the exact newly sent semantic message row and excludes only that row ID, not every response containing the prompt text.

- **Node.js `node:test` / `node:assert`: reused.** They already power the focused controller contract suite and are sufficient for deterministic fake-transport regression without introducing a new test framework.

- **GitHub Actions/merge queue: reused.** Existing protected CI and merge queue remain the release governance mechanism; no replacement CI/CD product is introduced.
