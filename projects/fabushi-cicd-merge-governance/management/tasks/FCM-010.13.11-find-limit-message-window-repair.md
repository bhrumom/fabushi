## Production blocker

The production `fabushi.app.find` schema accepts `limit <= 100`. The original external journey emitted `limit=200`, so the real production MCP correctly failed closed. PR #2553 introduced a shared serialization boundary that clamps/defaults valid find requests to `1..100` and rejects invalid non-positive/non-integer limits.

Independent exact-head review then exposed a second correctness issue: a broad `find({ role: "article", limit: 100 })` returns the first 100 matching DOM elements. Messenger rows are rendered oldest-to-newest, so a persistent conversation with more than 100 rendered rows can hide the newly appended assistant response from both the baseline and incoming-message poll.

## Repair contract

1. Every production `fabushi.app.find` still emits `limit <= 100`; invalid find limits remain fail-closed.
2. Send/receive message tracking no longer relies on the oldest-first capped article query. It reads a bounded semantic snapshot (`maxElements=500`), requires the exact `test:messenger-input` composer sentinel to prove traversal reached the end of the rendered message list, keeps only the newest 100 semantic message rows, and fails closed if the sentinel is missing.
3. The message baseline is captured before send, preventing an immediate assistant response from being absorbed into the baseline.
4. The production journey uses `createMessageReceiveTracker` for both baseline/send and incoming detection.
5. Deterministic regression drives that same production tracker through a fake device transport: 130 existing rows -> send -> own row + appended assistant row -> fresh snapshot -> exact assistant response detection. It also verifies the production snapshot arguments and fail-closed sentinel behavior.
6. Forward-peer lookup is narrowed by exact button name before the 100-result cap.
