## Root cause proven from canonical source

This failure is materially different from the already-fixed list-remount/stale-generation/`find limit` defects.

`third_party/mahayana/mahayana-rs/mahayana-runtime/src/kernel_conversation.rs` implemented `KernelConversationProvider::list_conversations()` by returning `Conversation::mahayana_assistant()`. The canonical helper initializes `unread_count` to `0`; the production provider therefore had no state capable of exposing a positive unread count after an assistant reply. Desktop Messenger projects the legacy peer unread state from `conversation.unreadCount`, so the exact App Surface marker could never become `unread-positive` on this provider.

A second projection gap existed at the Electron transport boundary: assistant `chat.message` completion updated the conversation journal but did not request a fresh authoritative `conversation.list`, so even a corrected runtime unread count would not necessarily reach the peer list promptly.
