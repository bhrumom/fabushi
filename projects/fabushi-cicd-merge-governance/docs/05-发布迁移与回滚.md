# 发布迁移与回滚

## CI/CD governance rollout

1. CI/workflow changes are proposed through a PR.
2. PR-head `CI result` and workflow-governance checks must pass.
3. Sensitive changes are explicitly reviewed/authorized.
4. GitHub merge queue validates the merge-group candidate.
5. After merge, canonical `main` is re-read and post-merge workflows are inspected.

## Store delivery rollout

- Apple/Google workflows remain `workflow_dispatch` only.
- Selected source resolves to an exact SHA.
- Release-source gate runs before expensive build/sign/upload steps.
- Failed ancestry or required platform gate stops delivery before upload.
- Successful upload artifacts are preserved and the exact delivered packages are published as immutable GitHub Release assets where the workflow supports it.

## Rollback

### CI / classifier regression

Revert the offending workflow commit through a PR; because workflow files are Tier 3, the revert still passes workflow guardrails and merge queue. Do not disable branch protection as the default rollback.

### Release-source gate regression

Revert or fix `.github/scripts/require-release-source-gates.sh` and the affected delivery workflow through protected main. Do not bypass the gate by manually uploading an unverified package unless an audited emergency process outside this project explicitly authorizes it.

### CODEOWNERS regression

Revert only the overly broad/incorrect ownership entries. A rollback must preserve explicit ownership for CI/CD and release infrastructure.

## Data migration

N/A: this governance project does not migrate application data. Owner: Fabushi maintainers. Revisit if CI/CD changes introduce persistent release metadata or deployment-state migrations.
