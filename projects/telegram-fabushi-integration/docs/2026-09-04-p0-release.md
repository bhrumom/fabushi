## Four-group contract

1. **Execution group** reads one authoritative task file, verifies live dependency state, changes only that scope, and writes the real branch/commit/PR/check/evidence/status/changelog back into that same task and project records. Planned/pending is never passed. It cannot self-award `REVIEW-PASS`.
2. **Code review group** starts after a pushed real diff and returns `REVIEW-PASS` or `REVIEW-REJECTED` against the exact reviewed head. Dependency contracts that are still `in-progress` cannot be treated as accepted.
3. **Test release group** starts only after task review pass and uses GitHub Actions. It must test an installable/package artifact and write back exact canonical-main SHA, app version, platform, workflow run/job, journey/test ID, timestamp, full video, step screenshots, trace, HTML/native report and logs. Pass and fail bundles upload through an `always()`-equivalent path, target 90-day retention or maximum platform limit with the limitation recorded.
4. **Formal release group** requires protected merge, exact accepted canonical-main SHA, the same package lineage, required packaged E2E and complete evidence. Missing any required field blocks closure/release; source-only green checks do not qualify.

For app-affecting tasks, `REVIEW-PASS` is necessary but never sufficient. The task must additionally record its own merge/CI/exact-main packaged E2E/Release evidence. No local build/test substitutes for GitHub Actions.
