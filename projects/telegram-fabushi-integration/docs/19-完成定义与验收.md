## 最终验收标准

只有同时满足以下条件，才可以认为“Telegram 能力已经完整融合进 Fabushi”：

1. Fabushi 不依赖 Telegram 网络即可独立完成账号、联系人、私聊、群组、频道、媒体、搜索、同步、通知、Bot/Agent、Mini Apps、支付、通话等目标功能。
2. Electron/iOS/Android 共享 Rust 通信核心，不存在平台各自重写核心逻辑。
3. 真人、Bot、Agent 使用统一 Participant + Conversation + Message 模型。
4. Bot/Agent 与真人可以在同一群和同一消息总线上通信。
5. Agent-to-Agent 通信真实可用。
6. Mini Apps 有自己的 SDK、权限、安全沙箱、开发者注册和发布链路。
7. 支付有服务端订单、PaymentIntent、验签、Webhook、Ledger，不是前端模拟。
8. 断网、重连、乱序、重复、多设备、服务重启均有自动化测试证据。
9. 桌面端核心交互完整、性能可接受，并通过 Playwright E2E。
10. iOS/Android 完成共享 Rust Core 接入与跨端消息测试。
11. 关键服务有 metrics/logging/tracing。
12. 敏感操作、Mini App 和 Agent 工具调用有明确权限边界。
13. 旧通信实现已经移除或明确进入只读迁移状态，不再双轨发展。
14. 所有目标功能在 Feature Matrix 中至少达到 E2E_VERIFIED，才能标记“完整实现”。
15. main 分支最终保持绿色：构建、单测、集成测试、E2E、协议兼容检查全部通过。

## 2026-09-05 — Protected-main evidence identity DoD

For a gate whose acceptance names an exact commit, “CI passed” means the required command actually executed on that exact accepted object; workflow/job association metadata alone is insufficient.

### Pull-request exact-head DoD

- final product head is immutable for the reviewed round;
- automatic `pull_request` canonical child is executed, not skipped/neutral/cancelled;
- raw evidence proves actual checkout/worktree HEAD equals that final product head before the authoritative command runs;
- `.github/scripts/assert-native-electron-canonical.sh` runs after that checkout and succeeds;
- same-run required `CI result` succeeds and reports the canonical child exact result `success`;
- independent review approves that same final product head; any later product commit invalidates the prior PASS.

### Protected merge-group DoD

- only after independent review PASS, protected merge queue creates a current `merge_group` commit;
- raw evidence proves actual checkout/worktree HEAD equals the current merge-group SHA, not the individual PR head;
- the unchanged canonical script runs after that checkout and succeeds;
- required same-group `CI result` succeeds with canonical child exact result `success`;
- canonical main is re-read after protected merge.

### Non-evidence

The following never satisfy an exact-head gate by themselves: green sibling checks, run/job `head_sha` metadata, a synthetic PR merge when product-head execution is required, a prior SHA, manual dispatch, rerun-only evidence, skipped/neutral status, or a relaxed/optional condition.

For `TFI-M6-MAINSAFE-001-VERSION-EXACT-HEAD-CHECKOUT-001`, #2343 fails this DoD because run `33930830358` / job `101208897330` actually checked out `265ceea6496b21ffdbd53d4fa8fc0b3374edd3ac` instead of product head `bf62cd9769cc24ae29fcf03c16a1f662bc7019aa`. Independent review #2344 / comment `5547912758` is therefore binding; #2343 is not merge/test/release authorization.
