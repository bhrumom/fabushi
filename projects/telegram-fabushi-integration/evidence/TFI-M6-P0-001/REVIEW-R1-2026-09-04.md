## Verified implementation findings that are correct

1. **`RespondCommunityJoin` compile boundary is repaired minimally.** `engine.rs` now builds `Option<Event>` explicitly rather than combining `bool` with `Option<Event>`. Approved Group/Channel processing produces `CommunityChanged` first and may then append `ConversationParticipantUpserted`; rejected processing produces only `CommunityChanged`.
2. **Requester/actor values in the implementation are not swapped.** `community.approve_join(&requester_id, &actor_id, ...)` makes the requester the joined member and the acting owner/admin the approver. The audit calls use `actor_id` as audit actor and `requester_id.clone()` as target. The additional `actor_id.clone()` changes for subscription audit targets are ownership-preserving compile fixes, not state-machine expansion.
3. **Community-backed `CreateConversation` stops before generic upsert.** In `service.rs::project_command`, an existing `CommunityState` for the same conversation ID returns `Vec::new()`. Because `handle()` returns immediately when no engine events exist, the repeated/forged create is a true service-level no-op: no cursor advance, journal append, generic `UpsertConversation`, retype, re-owner, or participant replacement occurs.
4. **Community-backed `UpdateConversation` remains metadata-only.** Existing logic maps only `title` and `description` into `Command::UpdateConversationInfo`; caller-supplied kind/owner/participants are ignored after community authorization.
5. **No-Community join regression remains fail-closed.** `RequestCommunityJoin` reads the existing Group/Channel conversation and then requires `state.communities[conversation_id]`; absence returns `EngineError::CommunityNotFound`. This PR does not synthesize `CommunityState::new()`.
6. **Non-Community create compatibility is preserved by the code path.** When no Community exists, `CreateConversation` still projects to generic `Command::UpsertConversation` under the pre-existing creator authorization.

These positive findings are not sufficient for `REVIEW-PASS` because the task requires task-specific semantic regression coverage and auditable open-source-first evidence, both of which still have material gaps below.

**Evidence:** `native/mahayana-messaging/tests/m6_channels_topics_contract.rs`, test `respond_community_join_emits_participant_projection_only_when_approved`.

- approved audit entry `action == JoinApproved`, `actor_id == human:owner`, `target_actor_id == human:approved`;

- rejected audit entry `action == JoinRejected`, `actor_id == human:owner`, `target_actor_id == human:rejected`;
- rejected requester is absent from members and removed from pending requests.

This is a real task-specific coverage hole because commit `726b4210ddd4d9a967778193a8d374b5f8bad206` exists specifically to repair moved requester/actor ownership values that Actions surfaced. Compiling the test binary proves Rust ownership/lifetime correctness; it does not prove actor-vs-requester semantic ownership.

**Required smallest fix:** extend the same named regression (or add one narrowly named P0-001 regression) to destructure both `CommunityChanged` events and assert the member/pending/audit predicates above. Do not add M6-P0-002 membership-recovery or M6-P0-003 admission-policy semantics.
