## Release and acceptance contract

After this version candidate merges through protected main, the canonical Electron main delivery must build and package Windows only in GitHub Actions and retain exact-SHA package/E2E artifacts. A GitHub Release used for the retest must contain the exact `fabushi-1.2.40-setup.exe` lineage and updater metadata bound to the accepted main SHA; an existing same-version Release must never be overwritten.

The Windows interactive workflow then installs the published installer, records before installation, authenticates the protected test account, exports only the bounded refresh-token-free App session, launches the installed Windows Fabushi App, and waits for that App to self-register the fresh run-bound `gha-<run>-<attempt>-windows-app` device. KRIS, historical devices and runner-owned gateways are invalid.

External acceptance must select only that newly registered device and make real successful calls through all six semantic tools: `fabushi.app.status`, `fabushi.app.snapshot`, `fabushi.app.find`, `fabushi.app.action`, `fabushi.app.wait`, and `fabushi.app.assert`. The complete Windows journey and real final `settings-logout` are required. Whole-session video, step screenshots, device-call trace, App stdout/stderr, release identity, report and failure diagnostics must be retained even on failure.
