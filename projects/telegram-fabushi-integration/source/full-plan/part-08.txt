

============================================================
二十九、PR 与分支执行规则
============================================================

为避免多个 PR 重复做同一目标：

1. 每个里程碑建立一个 Epic/Tracking Issue。
2. 每个 PR 必须关联唯一子任务。
3. 如果已有两个 PR 做同一件事：
   - 选功能更完整、架构更正确的一条作为主线
   - 把另一个 PR 中有价值的提交/代码 cherry-pick 或重构进去
   - 关闭重复 PR
   - 不允许两套并行实现一起长期存在
4. 所有跨模块变更必须附：
   - 协议变化
   - DB 变化
   - 测试证据
   - E2E 证据
   - 性能影响
5. 合并前检查 main 最新状态，避免基于过期分支继续大量开发。
6. main 永远保持可构建、可测试。


============================================================
三十、禁止事项
============================================================

1. 禁止为了“看起来完成”只复制 UI，不实现真实后端。
2. 禁止 Electron/Swift/Kotlin 各自维护一套消息状态机。
3. 禁止使用 Telegram API 作为 Fabushi 核心通信后端。
4. 禁止把 Telegram 账号当 Fabushi 身份主键。
5. 禁止把 Agent 继续做成另一套互不兼容的聊天系统。
6. 禁止 Mini App 直接获得主应用高权限。
7. 禁止支付成功仅依赖客户端返回结果。
8. 禁止未经许可审查直接复制第三方大段源码/资源。
9. 禁止在协议未版本化前大规模上线。
10. 禁止没有测试证据就宣布“完整实现”。


============================================================
三十一、第一轮立即执行顺序
============================================================

执行时不要从 UI 开始堆功能，第一轮按以下顺序推进：

Step 1：审查当前 main 与现有 Telegram 融合 PR
- 找到所有通信、联系人、Bot、Agent、Mini App、支付相关代码
- 查重 PR
- 识别已经完成的可复用部分

Step 2：建立 Telegram/Fabushi Feature Matrix
- Telegram Desktop/Unigram 功能逐项列出
- 映射 Fabushi 当前状态
- 给每项绑定源码目录、issue、测试

Step 3：固定 Rust Core API
- Participant
- Conversation
- Message
- Event
- SyncCursor
- Media
- Agent
- Payment
- MiniApp

Step 4：跑通最小真实通信闭环
User A -> Fabushi Gateway -> Message Service -> Sync -> User B

Step 5：让 Electron 完全使用新闭环
- 会话列表
- 消息列表
- 发送
- ack
- read
- reconnect

Step 6：再扩展媒体、群、频道

Step 7：Agent/Bot 接入同一消息总线

Step 8：Mini Apps + Pay 接入统一事件协议

Step 9：音视频与高级功能

Step 10：移除旧通信路径并做全量 E2E


============================================================
三十二、最终验收标准
============================================================

只有同时满足以下条件，才可以认为“Telegram 能力已经完整融合进 Fabushi”：

1. Fabushi 不依赖 Telegram 网络即可独立完成账号、联系人、私聊、群组、频道、媒体、搜索、同步、通知、Bot/Agent、Mini Apps、支付、通话等目标功能。
2. Electron/iOS/Android 共享 Rust 通信核心，不存在平台各自重写核心逻辑。
3. 真人、Bot、Agent 使用统一 Participant + Conversation + Message 模型。
4. Bot/Agent 与真人可以在同一群和同一消息总线上通信。
5. Agent-to-Agent 通信真实可用。
6. Mini Apps 有自己的 SDK、权限、安全沙箱、开发者注册和发布链路。
7. 支付有服务端订单、PaymentIntent、验签、Webhook、Ledger，不是前端模拟。
8. 断网、重连、乱序、重复、多设备、服务重启均有自动化测试证据。
9. 桌面端核心交互完整、性能可接受，并通过 Playwright E2E。
10. iOS/Android 完成共享 Rust Core 接入与跨端消息测试。
11. 关键服务有 metrics/logging/tracing。
12. 敏感操作、Mini App 和 Agent 工具调用有明确权限边界。
13. 旧通信实现已经移除或明确进入只读迁移状态，不再双轨发展。
14. 所有目标功能在 Feature Matrix 中至少达到 E2E_VERIFIED，才能标记“完整实现”。
15. main 分支最终保持绿色：构建、单测、集成测试、E2E、协议兼容检查全部通过。


============================================================
三十三、计划维护规则
============================================================

本文件作为“Fabushi Telegram 全量融合”的总执行基线，后续每轮开发都应更新：

- 当前里程碑
- 已完成项
- 未完成项
- 阻塞项
- 相关 PR
- 相关 commit
- 测试证据
- E2E 结果
- 下一步任务

任何新增需求都必须先映射到本计划中的模块；如果属于新的平台能力，再扩展本计划，避免形成孤立模块。

最终目标不是“Fabushi 里面有一个 Telegram”，而是把 Telegram 已验证成熟的即时通信产品能力，融合并重构成 Fabushi 自己的通信基础设施，并在 AI Agent 网络、Mini Apps、支付和跨端统一 Rust Core 上形成明显超越。
