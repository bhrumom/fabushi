# PR 与分支执行规则

- **项目**：Fabushi Telegram 全量融合
- **文档 ID**：MGMT-06
- **版本**：v1.0
- **状态**：BASELINE
- **基线日期**：2026-08-22
- **源计划**：`../source/完整telegram融合进fabushi.txt`

> 本文档由源计划结构化拆分而来。源计划未明确的管理字段会标记为“项目管理补充/待确认”，避免把推导内容冒充既有事实。

为避免多个 PR 重复做同一目标：

1. 每个里程碑建立一个 Epic/Tracking Issue。
2. 每个 PR 必须关联唯一子任务。
3. 如果已有两个 PR 做同一件事：
   - 选功能更完整、架构更正确的一条作为主线
   - 把另一个 PR 中有价值的提交/代码 cherry-pick 或重构进去
   - 关闭重复 PR
   - 不允许两套并行实现一起长期存在
4. 所有跨模块变更必须附：
   - 协议变化
   - DB 变化
   - 测试证据
   - E2E 证据
   - 性能影响
5. 合并前检查 main 最新状态，避免基于过期分支继续大量开发。
6. main 永远保持可构建、可测试。

## 禁止事项

1. 禁止为了“看起来完成”只复制 UI，不实现真实后端。
2. 禁止 Electron/Swift/Kotlin 各自维护一套消息状态机。
3. 禁止使用 Telegram API 作为 Fabushi 核心通信后端。
4. 禁止把 Telegram 账号当 Fabushi 身份主键。
5. 禁止把 Agent 继续做成另一套互不兼容的聊天系统。
6. 禁止 Mini App 直接获得主应用高权限。
7. 禁止支付成功仅依赖客户端返回结果。
8. 禁止未经许可审查直接复制第三方大段源码/资源。
9. 禁止在协议未版本化前大规模上线。
10. 禁止没有测试证据就宣布“完整实现”。
