# 03 架构与实现策略

## Current state
PR #1971 established `mahayana-kernel`, supervisor, orchestrator, workspace engine, model/native engine, MCP runtime/native agent and an explicit legacy bridge. `mahayana-product` still has Codex auth/secrets compatibility dependencies.

## Target architecture
`Electron/iOS/Android/Web/CLI -> Mahayana Protocol -> Mahayana Kernel -> Session/Workspace/Tool/Memory/Workflow/Extension/Model/Policy -> capability router -> native engines and optional vendor adapters`.

## Strategy
1. Pin upstream audit commits per round.
2. Build a capability/provenance matrix: upstream feature -> Mahayana contract -> implementation -> tests -> gaps.
3. Port concepts behind Mahayana-owned interfaces; do not expose vendor product types.
4. Move remaining Codex auth/secrets and app-server dependencies behind adapters or native replacements.
5. Add side-by-side conformance tests before deleting compatibility paths.
6. Keep Electron/native mobile canonical and use CI for heavy validation.

## Comparative strengths
Codex: mature safety/fail-closed approvals, app-server/thread/session behavior, MCP/connectors/skills/provider machinery and broad production compatibility.

Grok Build: stronger product-oriented long-running execution, worktrees/checkpoints/rewind, codebase graph, queue/steer, objective verification, attempt journal, permission memory, loop interruption, workflows/hooks/subagents, headless/ACP ergonomics.

## Known weaknesses to avoid
Codex coupling risk: deep vendor-specific types can leak into product contracts. Grok Build coupling risk: copying its product/runtime wholesale would simply replace one vendor dependency with another. Both require provenance discipline and capability-level integration rather than identity-level adoption.
