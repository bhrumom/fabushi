# 架构与实现策略

## 当前状态

`bhrumom/fabushi` 是 monorepo。`mobile/MIGRATION.md` 已明确产品有 Desktop、Android、iOS
三种原生壳和一个共享 Mahayana Rust Host；`frontend/README.md` 又承载 Web 与微信小程序；
`chatgpt-vps-control` 承载 Chrome/Browser 能力；后端、CLI、论坛、商城和 Marketplace 以
独立目录存在，但仍共享根级 workflow、项目记录和部分相对路径。

## 目标状态

```text
fabushi-governance                  portfolio / migration control plane
fabushi-platform-core               versioned Rust/runtime/contracts
├── fabushi-web                      Next.js / official site
├── fabushi-desktop                 Electron desktop
├── fabushi-android                 Kotlin + Compose
├── fabushi-ios                     SwiftUI
├── fabushi-wechat                  Taro / WeChat native mini-program
├── fabushi-chrome-extension        Chrome/browser control
├── fabushi-backend                 API / Worker / service runtime
├── fabushi-cli                     command-line client and release
├── fabushi-forum                   forum web platform
├── fabushi-commerce                commerce platform
└── fabushi-marketplace             official catalog/package distribution
```

## 迁移阶段

1. **M0 登记与冻结**：注册 PRS、固定 canonical SHA、完成路径矩阵和 OSS 调研。
2. **M1 建仓**：创建目标 GitHub repos，初始化 README/license/branch protection，不推送产品
   源码前先核对名称、可见性和 owner。
3. **M2 边界化**：把 Desktop 依赖的 Web shared/runtime 模块归入 Core 或 Desktop 包；把
   mobile 的 Rust host 依赖改为版本化 Core 产物；把 CLI 的 crates/harness 与 Core 依赖分开；
   清除源仓库相对路径。
4. **M3 导出**：在 GitHub-hosted runner 的 fresh mirror 中使用 `git-filter-repo`/必要时
   `git subtree` 生成每个目标仓库的历史，保存源/目标 ref 映射和路径审计。
5. **M4 独立质量门**：为每个 repo 迁移最窄 CI；平台构建、模拟用户 E2E、截图/视频/trace/
   报告和 Release 必须在目标仓库验证；CLI 还要验证 binary checksum 和跨平台发布清单。
6. **M5 切换**：更新 updater、部署和文档链接；源仓库只保留治理与迁移索引；保留 archive
   tag 和 rollback refs。

## 关键接口

- Core → Desktop：Rust sidecar / NDJSON host protocol 和版本化 host bundle。
- Core → Android：JNI/`libmahayana_app_host.so` release artifact。
- Core → iOS：C ABI static library/header release artifact。
- Core → Web/WeChat：版本化 API contracts、WASM/HTTP contract 和 npm package。
- Core → CLI：版本化 Rust crates、host protocol、配置/schema 和 release artifact。
- Backend ↔ clients：公开 HTTPS API/schema，不引用另一个 repo 的本地路径。
- Governance → repos：仅保存 project/repo matrix、CI contract 和 migration evidence。

## 设计取舍

初始阶段保留历史和可追溯性优先；共享 Core 独立出来避免把同一套 Rust 运行时复制到每个
平台。CLI 单独拥有命令行 UX、配置、安装器和 Release 节奏，但只能依赖已发布的 Core API。
若某平台必须暂时 vendored 依赖，则必须记录版本/来源并在下一阶段替换为 pin；不得把整个
monorepo 作为 submodule 继续隐藏耦合。
